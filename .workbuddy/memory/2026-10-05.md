## V5-dispatch：db_seed.js 改为「日期 + 时间」合成完整 timestamp（含 ±1 天跨天偏移）

项目：`D:/GitHub/All-js-project/packages/backend/full-web-backend/V5-dispatch`

### 背景
上一版脚本把 `d_plan_time/d_time/a_plan_time/a_time` 按 `HH:mm` 落进 `time` 列，
把原始值里的跨天后缀（`d_plan_time` 25 条 `(+1)`、`a_plan_time` 106 条 `(-1)`）**丢弃**了。
用户要求改成：日期 + 时间 → 完整 `YYYY-MM-DD HH:mm:ss`，带 ±1 的按 ±1 天挪。共 131 条受影响。

### 前置事实（用户早已把 schema 改好，非本次改动）
- `ecyilang` 四个时间列类型已是 **`timestamp(0)`（timestamp without time zone）**，
  `d_flight_date`/`a_flight_date` 是 `date`；`prisma migrate diff` 显示库与 schema 一致。
- 跑 seed 前 ecyilang 是 0 行（用户又 force-reset 过），无数据风险。

### ⚠️ 关键实测：`timestamp without time zone` 读写对称、不吃会话时区
用临时表 `_probe_ts` 对比「带/不带 `options: '-c TimeZone=UTC'`」两种连接：
写 `new Date(Date.UTC(2026,8,29,5,0,0))` → PG 文本两种会话下都是 `2026-09-29 05:00:00`，
读回都是 `2026-09-29T05:00:00.000Z`。**结论：用 `Date.UTC(...)` 构造，墙上时间就等于北京time，不漂移。**
（与 `timestamptz`/`date` 不同 —— 那两个必须固定 UTC 会话时区，见前一日记录。）

### 换算规则（固化在 db_seed.js）
| 目标列 | 基准日期 | 规则 |
|---|---|---|
| `d_plan_time` / `d_time` | `d_flight_date` | 日期 + HH:mm，带 `(+1)` 再加 1 天 |
| `a_plan_time` / `a_time` | `a_flight_date` | 日期 + HH:mm，带 `(-1)` 再减 1 天 |

- `d_flight_date`/`a_flight_date` 仍只取前 10 位存 `date` 列（`T08:00:00` 丢弃）。
- 本侧日期为空时退回用对侧日期（防御性，实测 0 次触发）。
- `date → Date.UTC(y, m-1, d + offset, H, M, S)`，跨月/跨年由 JS Date 自动进位
  （实测 `a_flight_date=2026-10-01` + `(-1)` 正确落成 `2026-09-30`）。
- 报告口径修正：时间为空时不再计入 `fallback` 统计（上一版把 190 条空时间行误报成 fallback）。

### 验证（全部通过）
- `pnpm db:seed` 跑两遍 → 均 359 / 15 / 67，幂等。
- **全量逐字段比对**：359 行 × 23 列 = **8257 个值，不一致 0**（校验脚本自身踩坑：
  用字符串做日期加 `pad(d+off)` 会算出 `2026-09-31`/`2026-10-00` 假报 24 处，
  改成真实 `Date` 加减后归零 —— 以后校验脚本别自己拼日期）。
- psql 抽查：落库文本确为 `YYYY-MM-DD HH:mm:ss`；`d_plan_time::date = d_flight_date + 1` 恰好 **25** 条，
  `a_plan_time::date = a_flight_date - 1` 恰好 **106** 条；时间非空但日期为空 **0** 条。
- fips / manual_fips / records_checklist / records_special 全部保持 0 行（未动）。
- 临时文件（`_verify.mjs` / `_probe_ts.mjs` / `_probe_ts` 表）已清理。

### 已知输出
- 5 个机场名不在码表里，对应 4 个码列留 NULL：**纳沃伊、芝加哥、迪拜阿勒马克图姆、鄂州、阿拉木图**。

## V5-dispatch：`src/` 全量重写（Prisma 标准用法 + utils 收口 + dayjs）

项目同上。用户要求：`src` 里直接重写，UUID 之类的辅助函数都放 `utils/`，
用足 Prisma（含 `include._count` 这类关系能力），并用 **dayjs**。

### 分层（现状）
`config/` → `db/`（prisma 单例 + fieldMeta 表结构文档）→ `utils/`（纯函数：date/uuid/text/httpError/asyncHandler/prismaError/airports）
→ `services/`（一表一模块，跨表关系收口在 flightService）→ `controllers/`（只解析入参 + 抛 HttpError）→ `routes/`。

### 两条「时间语义」的硬规则（写在 utils/date.js 文件头）
| 列 | 类型 | 取值方式 |
|---|---|---|
| `ecyilang` 的 `*_plan_time`/`*_time`、`*_flight_date` | timestamp(6) 无时区 / date | **`wall*` 系列，按 `dayjs.utc()` 取 UTC 部分** |
| `records_checklist.created_at/updated_at`、`records_special.createTime/updateTime` | timestamptz | **`cn*` 系列，`tz('Asia/Shanghai')`**；「某一天」用 `cnDayRangeUtc()` 换算成 UTC 区间 |
混用必差 8 小时。`fips`/`manual_fips` 的时间列是 varchar，原样透传。

### ⚠️ Prisma 7 + adapter-pg 的两个坑（已实测定位，务必记住）
1. **`create` 带「多个关系」的 `include` 会把两条 SQL 并发发到同一条 pg 连接** →
   pg 报 `Calling client.query() when the client is already executing a query` 弃用告警
   （pg@9 变硬错误）。实测：1 个关系不触发、3 个关系触发；`findUnique/findMany` 正常；
   **交互式事务内带 `include` 也触发**。
   → 铁律：**写操作一律不带 include（只 `select: { id: true }`），写完后再单查一次补关联摘要。**
   （`records_checklist` / `records_special` 的写路径已全部按此改造。）
2. **`ON DELETE SET NULL` 的外键下，删父表前必须先把子表删掉**。
   先删父表 → FK 立刻把子行外键清成 NULL → 再 `deleteMany({where:{fk: key}})` 一条都匹配不到
   → 留下「三个外键全空」的孤儿行。原 `deleteFlight`/`deleteManualFips` 就是这个顺序，已修正为**先子后父**。
   验证手段也要注意：按 `flightId` 查是验不出问题的（外键已是 NULL），**必须按 `callsign` 再查一次**。

### 其它落地要点
- 关系计数统一走 `include: { _count: { select: { checklists: true, specials: true } } }`，
  不再维护 `checklist_uuid` 之类的冗余列。
- `records_special` 已无 `belongTime` 列、也无任何唯一约束：
  「归属日期」改为**从关联航班推导**（只读字段 `belongTime`）；
  upsert 只能是「逻辑键 `findFirst → update/create`」（事务内），「新增」不会再 409。
- ecyilang 投影键 `<uuid>-d`/`<uuid>-a`：落进外键列前必须剥后缀（`utils/uuid.js`）。
  `getFlightPlan` 对**裸 uuid 退到有内容的一侧** —— 否则 `/api/fips/:uuid` 省略 source 时
  会「detectSource 认得出、详情却 404」自相矛盾。
- 新增 `callsign` 过滤到 `/api/checklist`；`/api/special` 增加 `/latest`、`/key/:callsign/:day`。

### 验证
临时端口 5195 起服务跑 **66 项断言全通过**（三个 source 列表/详情/原始行、码表 CRUD+409、
`_count` 回流、belongTime 推导、日期筛选、级联清理、上传 415/201、404 兜底）。
服务端日志已无 pg 弃用告警；测试数据与临时文件（`_*.mjs`、测试上传图）全部清理，端口已释放。

### 三个关键简化手法
1. **`source === 表名 === Prisma delegate 名`** → 读操作直接 `prisma[cfg.model].findMany(...)`，

   按白名单过滤、空串转 null、**没传的键不出现**，一套代码同时解决「字段映射」「未知字段」、
   「局部更新语义」三件事。manual_fips 17 个列零逐字段映射代码。
3. **子表不 join**：`linkOf(row)` 直接读行里的三个外键列反推 `source` / `flight_uuid`，
   零额外查询；`_count` + `specials(take:1)` 的 include 只用在**读**操作上。

### 被砍掉的接口（前端 `api/*.js` 里还引用着，需要时再补）

→ ecyilang 的 `?date=` 过滤是 OR 两列（`d_flight_date` / `a_flight_date`）。

### 保留下来的业务规则
- checklist：`status='submitted'` 且 `created_at` 超过 **24 小时** → PUT/PATCH 回 409。
- manual_fips 删除：数组形式 `$transaction([子检查单, 子台账, 父航班])` —— **顺序即先子后父**，
  数组事务天然按序执行，比交互式事务简单也更稳。
- `flight_no` / `checklist_category` / `callsign` 是 NOT NULL：显式传空视为「不改」。

## 【再精简 2】V5-dispatch：唯一冲突交给全局中间件，两个辅助函数下沉 utils

用户口径（原话）：「这些辅助方法（`codeData` / `rethrowUnique`）放到 utils 去」「通过数据库的约束不能实现吗?」

### 关键结论（实测）
- 唯一性**本来就**是数据库 UNIQUE 约束在把关 —— settingService 里从来没有「先查重再报错」，
  是 DB 直接拒绝。service 里那层 `try/catch + rethrowUnique` 只是把 **P2002 翻译成 HTTP 409**，
  这是 HTTP 层的活，应该放在**一个地方**。
- 于是把翻译下沉到 **server.js 的全局错误中间件**，service 里 4 个 try/catch 全删掉。
- ⚠️ **Prisma 7 + driver adapter 下 `err.meta.target` 拿不到列名**（临时探针 `_probe_p2002.mjs` 实测，已删）：
  meta 只有 `{ modelName, driverAdapterError: { cause: { originalCode:'23505',
  originalMessage:'重复键违反唯一约束"airplane_company_name_code_name_key"', kind:'UniqueConstraintViolation' } } }`，
  连 `err.message` 都是 `Unique constraint failed on the (not available)`。
  → 文案只能落通用兜底 `{ "error": "该记录已存在（唯一约束冲突）" }`；
  代码里留着 `meta.target` 分支，只为将来能拿到列名的情况。
- **全库唯一约束只有两张码表的 6 个列**（schema 里 `@unique` 共 6 处），
  所以这个全局兜底对 checklist / special / fips 零副作用（它们没有唯一列）。

### 改动
- **`utils/values.js` 新增 `cleanBody(body, drop = ['id'])`**：整份 body 都收（**无白名单**），
  空串/纯空白 → null、剔除 `drop` 里的键、没传的键不出现（= 局部更新）。setting 原来的 `codeData` 就是它。
- **`utils/http.js` 新增 `uniqueConflictMessage(err)`**：唯一冲突 → 客户端文案（见上面的坑）。
- **`server.js` 全局错误中间件**：`isUniqueViolation(err) ? 409 : err.status || 500`，文案同源；
  注释写明「唯一性由 DB 约束把关，service 不查重、不 try/catch」。
- **`settingService.js`**：删掉 `codeData` / `rethrowUnique` / 全部 try/catch，
  `create` 直接 `return prisma.xxx.create({ data })`。只留一条业务校验：中文名列 NOT NULL（新增必填 / 更新不许清空）。
- `test/05_setting.http` 两处 409 期望文案改为通用文案；`test/all_http.txt` setting 段补 409 说明。

### 验证（打 5183，热重载）
读：67 / 15、`q=abu` 命中 1、非整数 id 404、未知 kind 404、`q=顺丰` 命中 1。
